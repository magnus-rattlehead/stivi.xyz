# Zig Coding Adventures: Revisiting the Blaster Worm and the evil UNC path buffer overflow it used.

Most other programmers I've spoken with got into the craft through wanting to create games or mods
for games. My first foray into the world of software was through wanting to become a malware author.
I remember watching "The World's Worst Virus" (or something like that) which was literally just a
VBScript joke program that popped up a series of messages, but in my mind that was literally the
coolest thing ever. I started watching a lot of malware related Youtube videos and really wanted to
make my own. I started with skidded out batch and visual basic scripts with some of my own faulty
logic thrown in, to my magnum opus: a .NET based ransomware program that I wrote all on my own and
kind of worked (though it was trivial to bypass as the passkey used for encryption is stored in
plain text in the binary). Anyway I never got past that level in malware development as I focused on
writing more legitimate software and doing CodeForces problems, but in the age of "agentic
development" I've become nostalgic for a simpler time where we ran Windows XP and used peer-to-peer
sharing to pirate stuff. As a kid I always wanted to make a self-propogating network worm and
thought to revist one of the most iconic ones: The Blaster Worm. The reverse-engineered source code
is publicly available and well-documented. Reading it over it is clear that it's also from a simpler
time: the author's own code is quite amateur C code (though was way more advanced than what I as a
kid would write), while the actual interesting part (the exploit + shellcode) is copied verbatim
straight from the proof-of-concept. I decided to rewrite it in one of my new favourite languages,
Zig.

## Step one, getting to the vulnerable code

`RPCSS.EXE` listens on TCP 135 and uses the DCERPC protocol, which is typically used by programs to
call a function on another computer on the network as though it were a local function. It accepts
Protocol Data Units (PDUs) as messages. There are three components of a a PDU: the RPC headers,
which is mostly control fields, stub data, which is encoded via Network Data Representation (NDR)
and optional auth headers.For the exploit we send two PDUs:

1. The bind PDU, binds to UUID `4d9f4ab8-7d1c-11cf-861e-0020af6e7c57` (a DCOM activation interface).
   RPCSS accepts the bind and sets up the NDR stub marshaling machinery first.
2. Request PDU, `05 00 00 03` header (DCERPC request, opnum 0) followed by our NDR-encoded stub.

The stub is where the crime happens. Its only interesting field is a NDR Unicode conformant varying
string, declared by three dwords in `buildStubData` in `src/blaster.zig`:

```
[max count]       = 765   (uncpath_len / 2)
[offset]          = 0
[actual count]    = 765
```

Those are counted in wide chars, making the declared string 1530 bytes. RPCSS hands that string to a
routine that copies it into a stack buffer in its activation handler without the necessary bounds
check. The 880-byte `payload_space` used below is a layout constant in our code, not a measurement
of RPCSS's destination buffer.

Because the copy is a flat byte-for-byte copy (it just doesn't range-check how many wide chars), our
filler bytes land on the stack in order. We lay that filler out so the overwritten bytes are
executable x86 code when control lands there.

## Step two, crafting the overflow

The source defines seven unwanted byte values in `payload_bad_chars`: `0x00`, `0x0a`, `0x0d`,
`0x5c`, `0x5f`, `0x2f` and `0x2e`. `appendRandText` excludes these when generating filler; this
isn't a blanket restriction on the entire request, which also contains headers and explicit path
delimiters. We must also use fixed block sizes because the target-specific branches depend on the
layout. `buildPayload` pads the generated shellcode to exactly 880 bytes and rejects it at compile
time if it cannot leave the required minimum space for the NOP sled.

Copied low-to-high, so stub order = stack order:

| Bytes | Content                            | Purpose                                                                                                          |
| ----- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 4     | `5C 00 5C 00`                      | `\\` as UTF-16LE makes the string a UNC path so RPCSS takes the vulnerable path                                  |
| 32    | `0x90` NOPs                        | filler                                                                                                           |
| 2+2   | `jmpShort(16)`, `jmpShort(25)`     | short jumps emitted by the current `appendUncPath` implementation                                                |
| 12    | rets[2], rets[0], rets[1]          | the three 2000/NT4 return addresses, positioned on the stack slots those OSes spill into                         |
| 88+   | NOPs, then `EB 04`(4)/random steps | a "walker": executable bytes chained by 4-byte strides so random filler bytes between gadgets are never executed |
| 880   | payload                            | exactly `payload_space`, the NOP sled + our shellcode                                                            |
| 118   | "ntshiz"                           | NT4 SP3/4/5 gadget block with jump-backs into the sled                                                           |
| 360   | "xpseh"                            | the XP/2003 SEH block (detailed below)                                                                           |
| 4     | `5C 00 00 00`                      | closing `\\` + wide NUL, terminating the string                                                                  |

## Step three, the execution

For the sake of brevity, I'll stick to explaining the execution on Windows XP. The other targets
employ pretty much the same trick of overwriting a pointer, point it to the garget that jumps to the
stack.

The key here is Structured Exception Handling (SEH), Windows' mechanism for handling exceptions such
as invalid memory accesses. It's essentially a low-level `try`/`catch`: a program registers a
handler that Windows can invoke when something goes wrong. On the 32-bit Windows XP we're targeting,
these registrations form a linked list on the thread's stack, with its head accessible through
`fs:[0]`. Each record has a `Next` pointer to the previous registration and a `Handler` pointer to
the exception-handling function. Windows follows this chain looking for a handler that can deal with
the exception. Microsoft's
[explanation of x86 exception handling](https://devblogs.microsoft.com/oldnewthing/20220418-00/?p=106489)
describes this stack-based bookkeeping.

These records live on the same stack as the buffer we're overflowing, so we can overwrite the
pointer Windows will use when it tries to handle a fault.

The copy overwrites saved EBP, the active SEH registration record, and the return address. Finally
we fault and exit the copy to trigger exception dispatch into the corrupted SEH chain (on the other
targets we simple `retn` to our data).

XP's frame bookkeeping looks like:

```asm
push ebp
mov  eax, fs:[0]     ; load head of the SEH chain
push ebp
push eax             ; record = [Next][Handler] on our stack
mov  fs:[0], esp
```

Our filler overwrote the stack-top record (in the xpseh region at offsets 306..318) with:

```
[306] EB 06           ; jmp short, skips bytes 308..313, target = 314
[308] (2 random)      ; (the rest of the Next field, junk)
[310] 59 1C 00 01     ; 0x01001c59: RPCRT4.dll, XP SP0/SP1 pop/pop/ret
[314] 8B 44 24 FC     ; mov eax, [esp-4]
      05 E0 FA FF FF  ; add eax, 0xFFFFFAE0 -= 1312
      FF E0           ; jmp eax
```

RPCSS eventually faults (the copy mangles things deeper in the frame), so `RtlDispatchException`
walks the SEH chain from `fs:[0]`, finds our forged frame at the top, and calls the Handler field
with `(ExceptionRecord, EstablisherFrame, ContextRecord, DispatcherContext)` pushed. That call lands
at `0x01001c59`, a `pop / pop / ret`: the pops discard pushed context data, and the `ret` transfers
execution back up into the damaged frame region, landing on the `EB 06` short jmp, which skips the
ret dword and arrives at seh[314], the sled-builder:

```asm
mov eax, [esp-4]     ; EAX = a pointer near this frame (per HD Moore's empirics)
add eax, 0xFFFFFAE0  ; EAX -= 1312 -> back to the start of the NOP sled
jmp eax              ; into `0x90 x N` -> shellcode
```

Keep in mind that the recovery code uses a fixed backward displacement, so we must preserve the
surrounding block sizes.

## Step four, our shellcode

The sled ends at `bind_shellcode`, which is generated entirely at compile time. It's constructed
using the same builder logic used in msfvenom. I wanted its construction to be visible in the source
instead of keeping it in an opaque binary file.

`ShellcodeAsm` is a small byte emitter with labels and fixups, used by the three
`shellcodeBlockMain`, `shellcodeBlockKernel32` and `shellcodeBlockFindFunction` functions. The
`bind_shellcode` initializer builds and encodes their output and adds the decoder stub.

The decoded stage is a classic bind shell: it listens on port 4444, accepts a connection and starts
`cmd.exe` with its standard input, output and error handles set directly to the accepted socket,
which send over the tftp GET command and start the worm.

## Zigisms

My favourite part of this rewrite is how much of the construction can happen at compile time. I can
keep the generation logic beside the program that uses its output, without a separate generator
command or a generated source file to keep synchronized. That also moves some mistakes into the
build, so the machine code can be checked at compile time and if it's guaranteed to not work via the
inline assertions (this is still my responsibility to write assertions which I am historically bad
at) the code won't compile.

The logging helper is a nice example of generics without templates.The formatting code can check the
format against those types during compilation. `DottedIp.format` plugs a custom representation into
the same writer interface, so logging an ip address doesn't require allocating an intermediate
string.

The other great things about this are generic Zig stuff like sentinels, explicit integer operations,
Zig syntantic sugar and so forth. It really is a joy to write if you come from a C background. I
hope to write more malware in Zig, it truly is a joy!

You can check out the full source code [here](https://github.com/magnus-rattlehead/zig-blaster) if
you're interested.
